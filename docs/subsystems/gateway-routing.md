# Gateway routing and fallback

The gateway is agentlink's local LLM endpoint (`127.0.0.1:3425` by default). It
serves Chat Completions, Responses, Anthropic Messages and Gemini. It finds
the provider, key or account and model for each request. When the upstream
doesn't speak the agent's API, the gateway translates. When an upstream
fails before any of the reply is sent, the gateway moves to the next
candidate.

This page covers how a request is routed. Plugins that change requests and
replies are in [Gateway middleware](gateway-middleware.md). Subscriptions
served by a plugin are in [Provider and plugin ownership](provider-plugins.md).

WorkBuddy and CodeBuddy Code's `X-Conversation-ID` is a native session header
in `sessionHeaders` (`sessionOf`, `nativeSessionOf`, `conversationID` in
[`gateway.go`](../../internal/gateway/gateway.go)). It keeps their requests
apart even when two chats have the same first message. The same identity is
used for affinity, usage and the Routing page, and is preserved when passed
to a remote agentlink, not copied to an ordinary vendor. Existing header
precedence is unchanged. Affinity previously kept under an inferred first
message digest is not migrated to a newly recognised native id, so the first
request after upgrading can choose an account anew. Historical usage is not
backfilled; see [Gateway Session Aggregation](gateway-sessions.md).

Every route is wrapped in `counted`, `corsGuard`, `callerGuard`, `withCaller` and `keyLimited`; `/v1/messages`, `/messages` and `/v1/messages/count_tokens` in `keepsSignIn` too. `corsGuard` (#1051) serves CORS only to the origins listed in Settings › Network › Web pages (`settings.CORSOrigins`, cleaned to `scheme://host[:port]` by `settings.CleanOrigins`, which refuses a wildcard). A browser extension's own pages, popup and service worker are listed the same way by their origin, which is the browser's scheme and the extension's id: `chrome-extension://<id>` (Chromium, the id 32 letters a–p), `moz-extension://<uuid>` (Firefox, the Internal UUID about:debugging shows, not the add-on id) and `safari-web-extension://<uuid>` (Safari, which picks a new UUID on each launch, so a listing lasts until Safari restarts); the id must have that browser's shape, cased any way, and nothing else is taken — no bare scheme, no wildcard, no path (SkyAerope on Discord: an extension without host permissions is held to CORS like a page). A content script's fetch carries the page's origin, not the extension's. A listed extension is treated exactly as a listed page, below; one not listed passes as before (other schemes, below) with no CORS headers. For a listed origin it answers the preflight (204) and adds `Access-Control-Allow-Origin`, and every other request from it needs an enabled gateway key (`access.Authenticate`), even on loopback, or gets a 401. It takes the key from the caller `lanGuard` recorded too, since on the running server `lanGuard` has already put agentlink's own token in the key's place. Any other web page is refused 403 on every route (`foreignPage`): on loopback a call needs no key and the body's Content-Type isn't checked, so a page the user visits could otherwise send a "simple" `text/plain` POST and spend their subscriptions blind. Only an `http`/`https` Origin is judged, and one on this computer (`localhost`, `*.localhost`, `127.0.0.0/8`, `[::1]`, any port) or the request's own origin (its host and port equal to `Host`, such as a page on the gateway's LAN address) passes, as does useagentlink.ai on `/v1/agentlink/omarchy`. Other schemes (`app://`, `file://`, `tauri://`, `vscode-webview://`, `chrome-extension://`) come from desktop apps, webviews and extensions that don't enforce CORS, and pass keyless as before; `null` is not one of them, since any web page sends it from a sandboxed frame and an opened file sends it too, so a call with it needs an enabled gateway key as a listed origin's does, and is answered 403 without one (no CORS headers either way, so a frame or a local page still reads no reply). A page at a subdomain of localhost (`localhostSubdomain`, #2256) needs a key the same way: Chrome and Firefox resolve `*.localhost` to loopback themselves, but Safari and other WebKit views ask the system resolver, which before macOS 26 asks the network's DNS (WebKit bug 160504), so a resolver that answers serves such a page from anywhere. `tauri.localhost` and `wails.localhost` stay keyless on Windows only, where Tauri's and Wails' webviews serve themselves at those names; on macOS and Linux those apps use `tauri://` and `wails://`. A request with no Origin (every agent's) passes through with no CORS headers, as before. A page whose own name resolves to 127.0.0.1 (DNS rebinding) would count as same-origin here, so `lanGuard` refuses it first (`rebound`, 403): a loopback request carrying a browser's marks (`Origin`, `Sec-Fetch-Site`/`Sec-Fetch-Mode`, a `Mozilla/` user agent) whose `Host` isn't this computer's (an IP, `localhost` but not a subdomain of it, which WebKit asks the DNS for (#2256), a container runtime's name for the host such as `host.docker.internal`, `AGENT_LINK_PUBLIC_URL`'s or `AGENT_LINK_ADDR`'s host, the machine's own name) needs an enabled gateway key. Agents send none of those marks and pass under any name. Before any of that, `lanGuard` lets in one request without a key from anywhere: `POST /_agentlink/claude-mcp/<token>` with the token of a Claude subscription run now live (`ownCallback`, see [the Claude subscription bridge](claude-subscription-bridge.md)), the run's MCP helper calling back to a `AGENT_LINK_ADDR` that isn't loopback (#1546). Next, before the key or `rebound` is looked at, the allow list (lc on Discord, agentlink in Docker on a public host): with `AGENT_LINK_ALLOW_IPS` or Settings › Network › Allowed addresses (`settings.AllowIPs`, this computer's own, never brought by a sync or restore: see [sync and backup](sync-backup.md#what-stays-on-each-computer); the variable wins and the page then only shows it) naming IPs and CIDR ranges, a request whose connection (`RemoteAddr`, IPv4-mapped IPv6 unmapped, zone dropped) is outside them is refused 403 naming its address, even with an enabled gateway key (`refuseNotAllowed`). Loopback and this computer's own interface addresses always pass. A forwarding header is never taken for the address, so a proxy or tunnel on this computer passes (it arrives from loopback) and its clients are limited at the proxy. An entry that doesn't parse lets nothing in and is logged once; the list stays on. No file, or an empty one, is no list. The Settings page's saves read with `LoadChecked` too and refuse such a file, as `settings.Save` does. `agentlink web`'s server is wrapped in the same check (`AllowGuard`). | One try | `attempt` sends one candidate the request. It goes through the proxy of the account or key it uses, else the provider's (`p.Via`, `ProxyChoice`: `AccountProxies` holds an account's by its name, a key's by its `KeyID`). A request agentlink makes for one provider while serving another's (a web search, an image description, a classifier call) takes its own provider's proxy or the global one, never the outer one: `netproxy.With` replaces a choice the context already names, "" too, and `webSearch` starts from none, so the search APIs follow the global proxy (#1522). A local proxy that refuses the connection is retried directly once when the request is replayable, so stopping a local proxy does not turn a reachable vendor into a 502; remote and provider-owned proxies remain authoritative. A provider of the user's set not to check its certificate (`InsecureTLS`, #2383) has it skipped for its own base URLs' hosts alone, through `p.Via` ([Providers and accounts](providers-accounts.md)). Every request to one vendor's host shares one HTTP/2 connection (`upstreamTransport`); one with no frame for 20s is pinged, and dropped when no answer comes within 10s (`netproxy.HTTP2Health`, on `http.DefaultTransport` too), so a connection gone silent without closing (a proxy's way out died, a NAT forgot the flow) fails the requests on it, which move on as a 502 does, and the next request dials a new one. A live vendor answers a ping whatever its streams are doing, so a long wait for a first byte is not cut by it (#2843: a group's requests hung with no first byte until a restart; `TestGroupMovesOnFromSilentHTTP2Connection`). ## Codex titles, descriptions and predictions

Codex's title and description requests are independent hidden turns. The
settings `CodexTitles` and `CodexDescriptions` select their models separately;
an empty setting preserves the requested model. On a Agent Link model, both
paths wrap plain model text in the object Codex requested. Titles use
`{"title": ...}`; descriptions use `{"description": ...}` with nonempty text
and no invented maximum length. Title Off mode does not disable descriptions.

`codexTitlesTo`, `codexDescriptionsTo`, `codexTitle` and `codexDescription` in
[`codex_titles.go`](../../internal/gateway/codex_titles.go) own this selection
and response wrapping. Both the Responses API and Codex backend entrypoints
use it. Usage and Routing retain the original purpose; unusable description
answers are recorded as description failures. These helpers do not decrypt
foreign sealed history or repair ChatGPT's response protection.

Codex's composer predictions (#1970), its guess at the user's next message,
are another hidden turn on a fork of the thread, sent only through the
ChatGPT sign-in, with `thread_source` `composer_predictions`. Each one reads
the whole conversation again. `CodexPredictions` selects where they go: empty
sends them as Codex asked, `off` answers `{"suggestion":null}` from agentlink
and sends nothing (`sentNowhere`, as title Off mode), and a model id sends
them to that model. `codexPredictionsTo` and `codexPrediction` own this, at
the same two entrypoints. A model's answer reaches Codex only as the
`{"suggestion": string|null}` object it asked for (`predictionJSON`): plain
text is never taken as a suggestion, as Codex would put it in the user's
composer as their next message, so it gives no prediction and the call is
recorded as a prediction failure (`noPrediction`).

## Runtime path

1. `handle(proto)` reads the body and the model (`requestBody`, `requestModel`), then calls `serveAgent`. Every route that reads an agent's body (each API, count_tokens, Gemini's, embeddings, images, videos, System One, the Codex backend path) reads it through `readBoundedRequestBody` in [`request_bounds.go`](../../internal/gateway/request_bounds.go). It decodes a `Content-Encoding` of `gzip` or `zstd` (`decodedBody`; Codex sends zstd to a custom provider's `/v1/responses` too, #1223) and drops the header, so the provider is sent plain JSON, with one exception: a ChatGPT account's turn (POST `CodexBase`/responses, from the accounts loop in `forwardOnce` or relayed by `codexUpstreamOn`) is compressed again with zstd and a window of at most 2 MiB, as Codex's own client sends it (`provider.CodexCompressed`; openai/codex `responses_request_compression` and `http-client/src/request.rs`). It is compressed once the body is final, and again on each try. `/responses/compact`, an API key's requests and every other provider stay plain. Sent plain, a 1.1 MB text-only turn was answered 503 (ylorn on X). The plain body is what agentlink keeps and shows, and `codexDropped` judges a reset by the bytes that went on the wire. `codexDropped` also reads Envoy's 507 "exceeded request buffer limit while retrying upstream" (the backend failed and the front couldn't retry a body that large) as that reset, at any size, told as a 503 so agentlink, Codex and pi ask again and nobody rests (#2034). The size limit (`defaultBodyLimit`, 512 MB) holds for the decoded bytes (413), and any other encoding is refused 415. It was 128 MB until a long Codex session that had read many images went past it decoded, its inline screenshots resent each turn, and got the 413 on all five of Codex's retries (#1422, `TestImageHeavyCodexTurnIsRead`). agentlink's own 413 says it is agentlink's gateway limit, with the size, and that the provider was not asked (`overLimit`); `writeError` adds to any 413 it isn't holding that this is a byte limit, not the model's context, and to `/compact` or start a new conversation (`TestOverLimitSaysWhoseAndWhatToDo`). Every shape but Gemini's types a 413 `request_too_large`, Anthropic's own type, which pi's overflow table knows: pi compacts and tries once more rather than stopping on an OpenAI-shaped `api_error` (@wilsonxuuuu on X, `TestPayloadTooLargeSaysRequestTooLargeToPi`). `keyLimited` reads a limited key's compressed body the same way, so its reservation is the decoded size. `serveAgent` runs the [middleware](gateway-middleware.md) chain, then `serve`.

A Gemini-protocol client's request is left as it came, as for every effort agentlink sets. `cleanRules` refuses a value outside `provider.Efforts` and a pause with one. The try records it (`Try.RuleEffort`), and the Routing page says the rule set it. `rule_effort_test.go`, `grouprule_useeffort_test.go`, `routing-rule-effort.test.cjs`.
   - A rule by folder (`Rule.Folders`, `folders=~/work/acme,~/oss`; Cario0x on X: routing by the project being worked on) matches when the folder the agent works in is one of them or inside one (`provider.FolderUnder`, [`rulefolder.go`](../../internal/provider/rulefolder.go)): at a path's boundary, so `/a/b` is not under `/a/bc`; `~` is the home folder; a Windows drive is one with its WSL mount (`C:\work` is `/mnt/c/work`) and a `\\wsl$\<distro>` or `\\wsl.localhost\<distro>` share is the distro's own path; case doesn't count on macOS and Windows, nor ever for a drive. A rule outside folders (`Rule.ExceptFolders`, `except-folders=~/big-task`; #1606, Ti800) matches when the folder is in none of them, and an agent that says none isn't known to be in one, so it matches; a rule may have both (`Rule.ByFolder`, `inFolders`). The folder is read from the request only when a rule of the group has folders or except-folders (`workDir` in [`workdir.go`](../../internal/gateway/workdir.go)), in each agent's own words, taken from captured requests: Claude Code's ` - Primary working directory: <path>` (its `<`/`>` as entities; ` (was <old>)` after a change dropped), Codex's `<environment_context>` `<cwd>`, Pi's `<cwd>` in the system prompt, and OpenCode's `Working directory:` inside its `<env>` block. Only the system prompt and the user's and system messages' text count, never the model's words or a tool's result, and the last said wins. An agent that says none has no folder, and no `folders=` rule matches it (unknown, never empty). The same reading tells a plugin's fetch where its agent works ([provider-plugins](provider-plugins.md#where-the-agent-works-for-a-plugins-fetch)). A pause rule may hold by folder too (below). The trace's `RuleHit.Folder` is the folder read, and the Routing page tells it beside the rule's `folder …` condition. `TestFolderUnder`, `TestRuleMatchesByFolder`, `TestParseRuleFolders`, `TestWorkDirOfEachAgent`, `TestRuleByFolder`, `TestRuleMatchesExceptFolders`, `routing-folder.test.cjs`. Rules by folder are never in a shared group (`ShareGroup` drops every `ByFolder` rule).
   - A pause rule (`Rule.Pause`, `pause=<model>`; John on Discord: a model of the group paused in its vendor's peak hours) leaves the model it names out of the group while it holds (`provider.PausedOut`, on `ruleClock`): the group's own rules and each nested group's on the way down to a member, a group named taking all its models, and a model named taking it wherever a group in the group has it (#625). It runs before planning, on every request rather than once a turn, so the model is not first, not a failover, and not kept by affinity, and comes back as soon as the hours end. It holds by hours, days, agents and folders only (`cleanRules` refuses another condition), and is not a send-to rule: `Matches`, `MatchRule`, `ThenUses`, `Ruled` and the compaction rules leave it out. A send-to rule naming a paused model finds it unready and the group routes as without it. The trace keeps what was paused (`GroupRef.Paused`), and the Routing page says so. Every model paused answers 503 (`pausedError`) naming each rule. Embeddings go by the same pauses; manual groups have no rules (`Live`), so none pause there. A pause by folder (#1606, Ti800: a subscription's quota kept for the long task in one folder, `pause=<model> except-folders=~/big-task`) reads the folder only when such a pause is on the way (`provider.PausesByFolder`, then `workDir`): outside its except-folders, which includes a request that says no folder (a subagent's or a small model's that doesn't), the model is left out; with `folders=`, only requests known to be in them. Embeddings and System One's decision calls have no folder. `Paused.Folder`/`ByFolder` carry what was read, and the Routing page says the folder or that none was said. `rules_pause_test.go`, `TestPauseByFolder`, `TestPauseByFolderRule`, `TestParsePauseByFolder`, `routing-pause-folder.test.cjs`.
3. Candidates come from `planGroup` for a group or `plan` for a provider. They are filtered by `sealedReaders` and `allowedCandidates`. An account past its share is held out of the candidates (`capHeld`): a usage cap's share, each window at its own where the account gives it one (`AccountWindowCaps`, willz on Discord: 50% of the five hours, 40% of the week) and at the account's cap otherwise, or 100% of a window for a Codex account set not to spend its credits (`provider.HoldCaps`, `WindowCaps.Of`, `CodexNoCredits`). A ChatGPT account's call on `codex-auto-review`, which OpenAI counts in no window, is held by no usage cap, only by credits it may not spend (`freeOnChatGPT`, #1593, `TestAccountCapLetsAutoReviewThrough`). The account is held while any window is past its own share, and `cappedError` and the trace name the fullest such window's share and cap. When every candidate is held and one held for its credits spends its resets by itself, `autoReset` spends a reset on it and it is tried (`planned.held`); otherwise a capped or barred set returns `cappedError` or `barredError`. Then `affine` moves the conversation's last answerer first, unless it is resting or nearly used up. An `X-Agent Link-Account` header (`AccountHeader`) pins the request to one account: only that account is tried, and when it can't answer the caller is told why.
4. The candidate loop calls `attempt` on each candidate in turn, through a `holdWriter`. The writer holds the reply until it is clearly passing. A candidate that fails before anything is sent rests (`failure`): out of credit for 30 minutes, out of quota until reset, rate limited until retry-after, otherwise a minute and longer on repeats: doubled each time, up to `longestRetry` (10 minutes) for a failure and `longestRateRest` (30 minutes) for a rate limit back as soon as its rest is over, or up to the provider's own `restCap` in minutes (`Provider.RestCapOr`, at most `MaxQuotaRest`; `agentlink provider rest-cap <id> 4h`, #2008: a free key down for hours was asked every 10 minutes). A time the vendor names stands over it as before (`TestOwnRestCap`). The failure count is kept per key or account (`restKey`), and any of its models' answers clears it (`served`). Each model's own count (`restID`) is kept beside it and cleared only by that model's answer (`servedCandidate`): once it is past the account's, a sibling model answered since it last did, so the failure is the model's and it climbs its own ladder and rests alone, its siblings still served (#2241, weizsw: an Antigravity seat's gemini-3.5-flash-lite rested a minute 41 times of 43 while gemini-3.8-flash kept answering; `TestModelLadderClimbsPastSiblingAnswers`). Every model failing with no answer between still climbs the account's ladder and rests the account, and a candidate naming no model has the account's count alone. `rest-cap <id> off` (`provider.RestCapOff`, `restCap: -1`) is for a relay or account pool whose unknown errors come now and then and pass by the next request (Kismet Alan on Discord): a failure that says nothing of why (`failOther`: a 5xx, a dropped connection) then rests nobody and isn't counted, its trace rest `by: "off"` with no time left. A 401 or 403, a model not served, an account's window full, a rate limit (agentlink's own 30-minute cap), quota, credit and a restriction still rest it as before (`TestRestCapOff`). The shortest cap otherwise is a minute, the first rest; `rest-cap <id> 30s` is turned away and names `off`. A 400, 403, 404 or 422 that says the model isn't served (`unservedWords`) and says nothing of quota, credit or a rate limit rests only that key's or account's model (`modelRefused`, keyed by `restID`, its backoff counted apart): its other models are still served first in order (#1235, SenseNova's 403 "model is not available in the current token plan"). A Google account's Code Assist (the Antigravity and Gemini CLI built-ins) answering 404 `NOT_FOUND` ("Requested entity was not found.") rests its model the same way, as its endpoint is the same for every model (`codeAssistModelMissing`; Packing1 on Discord: Argon, listed for a Google AI Pro account, answered 404 and rested the whole account; `TestCodeAssistMissingModelRestsTheModel`). A refusal for want of quota, credit or rate, for an account its vendor restricted, or for a verify it asks of its account there, from another computer's agentlink (a Remote agentlink provider, LAN share) rests only the model it was about (`remoteModelRest`, keyed by `restID`, in `restAfterMarked` and `rateRest`): that agentlink serves each of its models from its own providers and rests them itself, so one out of quota there says nothing of the others (bigsteven on Discord: a 429 for one model rested every model on the remote for the 3 hours it named, so a group never moved on to the remote's other models; `TestRemoteAgent LinkQuotaRestsTheModel`, `TestRemoteAgent LinkRestrictedRestsTheModel`). Its key refused, the computer unreachable, or the key's own limit there (`keyLimited`'s 429, which carries `X-Agent Link-Limit-Reset`, `remoteKeyLimitHeader`), still rests it whole: #2077's reporter had a Claude Code session limit on the other agentlink refuse its Qoder models here (`TestRemoteAgent LinkRestsTheModel`, two gateways over HTTP; `TestRemoteAgent LinkKeyLimitRestsTheKey`). A 400, 404, 410 or 422 that says the model is retired (`retiredWords`: OpenCode Zen's 410 `ModelDeprecated` "Model exo-free has been deprecated.", whose own model list still names it; MOMO on Discord) rests only that model the same way, is retryable so a group's next member or another provider of it is asked, and is remembered (`provider.Retire`, `retired.json` beside `providers.json`): the model leaves that provider's entries in the catalog (`buildEntries`), so /v1/models, every agent's model list and the found groups go without it, until a request on it is answered again (`Unretire` in `servedCandidate`) or a week has passed. A refresh of the vendor's list doesn't bring it back early, since that list is where it still is. A `provider/model` request for it is still sent. A 400 or 422 that says this upstream's API can't take the request's shape (`shapeWords`: xAI's 422 "unknown item type" (#350), OpenAI's "Unknown parameter", and a limit of a model's own on tool schemas, OpenCode Go's 400 "JSON schema exceeds the maximum nesting depth of 10 levels" on muse-spark-1.3-contributor, #1870), or that it is served on another API than the one asked (`wrongEndpoint`, once the member has tried every API it has a URL for: #2670, a relay with a Chat URL alone refusing tools with reasoning and `none` too), rests nobody: the next candidate is asked once (`shapeRefused`, `failShape`), and the last one's error reaches the agent. A request missing what every API requires ("field required") isn't one, nor is a 200 that mentions it. Command Code's Provider API turning a request away with nothing but a trace id (`unsaidWords`: `{"message":"invalid request error trace_id: <hex>","type":"invalid_request_error"}`, a 400, or a 422 before) is handled the same way: it turns away a request whose history and asked-for output together are over a limit below the model's listed context (the reporter's A/B: one ~748K-token agent conversation answered 200 with `max_completion_tokens` 64000 and this 400 with 384000, the model's listed max output), which another member's model may take, and the key is fine (#2313, `TestGroupFailsOverCommandCodesBare400`). Its overflow, which names the model's context length before the trace id, and an error that names a `param`, aren't one. A relay's own cap on one request's input that says so (`tooLongRe`: B.ai's 400 "Input token exceed the limit", on a 380K request under the model's 1M window; #2445, worksyang) is taken as an overflow (`overflowed`), which no word list of `retryable` matched: a group's next member that may hold the request is asked (`withRoom`, `failOverflow`), nobody rests, another account of the same model isn't asked, and with no member left the agent is told the conversation is too long, so it compacts. A rate limit worded with input tokens (`paceWords`) isn't one, and a plain bad request is still asked of nobody else (`TestRelayInputCapGoesToTheNextMember`). A subscription account that fails any other way with a window full, by agentlink's latest reading of its windows, rests until that window renews. Both quota rests and window rests are held to `longestQuota` (8 days), so a reset time read wrong (a year off) doesn't bench the account for that long. The next candidate is then tried. A failed provider waits `fallbackCooldown` (1 minute) at the back. A WorkBuddy account the vendor restricted (#1849: 403 `{"code":11140,"msg":"request illegal","displayMsg":{"en":"Your account has been restricted due to unusual activity",…}}`) rests `restrictedRest` (2 hours) as `restricted` (`failRestricted`), not the minutes of an unknown failure: only WorkBuddy lifting the restriction, after the user's appeal, brings it back. Both shapes are known: the built-in's `wbExplain` and the plugin's `explained()` (0.1.17, the mover's `min`) end the error with `provider.WBRestrictedHint` (`restrictedSaid`), and the vendor's own body, its code 11140 or its words (`provider.WBRestricted`), counts only from a WorkBuddy candidate (`restrictedRefused`, `isWorkBuddy`), as another vendor's 11140 is its own. Bare "request illegal" isn't matched. WorkBuddy's 11128 channel refusal stays `promptRefused` and rests nobody. The Routing page names it "account restricted by the vendor", says the appeal is the way back, and gives the account's row a button that lifts the rest (`/api/gateway/unrest`) once the vendor has. Every other rest a key or account takes (quota, rate limit, retry-after, a failure's backoff) can be lifted by hand the same way (#1869): "Try now" on its row on the Routing page and beside its rest note in the provider's key list. It ends the rest only: the backoff count stays, and a refusal after it rests the key again the usual way. The vendor's safety filter refusing a reply rests nobody, whether it refuses the turn before any of the reply is said or once some of it has been said (`refused`, `refusedAfter`). Its note on the try (and in the error the agent gets when nobody is left) is the vendor's reason, with Anthropic's `stop_details` category and explanation when it gave them (`refusedDetail`, #1768: "safety filter: refusal (category cyber)"); none is made up when it gave none. `stop_details` is carried through the IR (`Event.StopDetails`), so a Claude subscription run through the claude CLI and a translated Anthropic route keep it for an Anthropic client too. How many more candidates a refusal before any of the reply is asked of is Settings' `RefusalRetries` (`refusalAsksAgain`, counted per request in the candidate loop; a group's other members count too): unset, every one left (#248); 0, none (#1925, DD on Discord). When nobody is left, an agent on Anthropic's Messages API gets the held refusal itself, the vendor's 200 with `stop_reason` `refusal` and its `stop_details`, streamed or whole (`holdWriter.handBack`), since that is what Claude Code switches to its fallback model on; a 400 is only an API error to it. Codex and Chat clients still get `failTo`'s 400 (`refusedStatus`), which they don't ask again for. `TestRefusalRetries*` in [`refusal_retries_test.go`](../../internal/gateway/refusal_retries_test.go) cover keys, a group and the Claude subscription. The ChatGPT backend's 502 "response protection is unavailable" is about the request's content, not the account: the same history fails the same on each of its accounts and models. It rests nobody, isn't tried again after a moment, and isn't asked of the provider's other accounts or models; another provider left in a group is asked once (`protectionRefused`, `elsewhere`). One cause is known (#1270): a history that replays the backend's own `web_search_call` in a request that doesn't declare the `web_search` tool is refused so, whatever the account, model or turn (a plain turn, a thread's description, a compaction, Codex's own text compaction for a custom provider with `tools: []`). Every request to the ChatGPT backend with such a history therefore declares cached-only search (`{"type":"web_search","external_web_access":false}`, `provider.DeclareSearch`): an account's in `codexBody`, Codex's own sign-in relayed in `codexUpstreamOn`. It goes in the tools, or for Responses Lite (its header, `reasoning.context` `all_turns`, or an `additional_tools` item already there), which refuses a top-level `web_search`, in the `additional_tools` item. A request that offered no tools gets `tool_choice` `none` so the model can't search; one with a forced choice keeps it. A history without a search, or a request that declares search already, is relayed unchanged. siwc, API-key requests to openai.com and the legacy `/responses/compact` are left as they were.
5. The last candidate's error reaches the agent, with one exception for a group (#1418, `patience.go`). When every member has failed in a way that passes (`busy`: 408, 500, 502, 503, 504 or 529 that isn't a proxy, a quota, response protection, or an upstream that answered a stream request with a whole reply, which fails the same however often it is asked (`didNotStream`; the same-one retries of `passing` leave it alone too, `TestStreamlessMemberIsAskedOnce`), or a 429 that is a short rate limit, not a plan or credit), and nothing of the reply has been sent, the members that failed so are asked again in turn after a pause (`replan`). The pause is `retryPause` doubled each round up to `replanLongest()` (30 times `retryPause`, 30s), and never shorter than the soonest Retry-After; a member whose Retry-After ends past the pause is asked after the others. This goes on while the group's `Patience` lasts. A member of a group in the group uses the innermost that sets `Patience` (`innerPatience`, #2410), as FirstToken (#2246) and Sink (#2255) do; unset falls back to the group asked for, and an inner `PatienceOff` skips replan for that member (`TestNestedGroupPatienceThroughOuter`, `TestNestedGroupPatienceInnerOff`, `TestNestedGroupPatienceFallsBackToOuter`). `replanRounds` (12) is only a backstop that never comes first: the pauses alone add up to `PatienceLongest` in 11 rounds (with 6, a group set to 240s gave up after 90s of pauses, real-jacket on #1418; `TestPatienceIsUsedUp`). The budget is the group's `Patience`, counted from the first time every member had failed, when the agent would have had the error (`waitFrom`; `Group.Waits`: 0 is `PatienceDefault`, 60s; -1, `PatienceOff`, turns it off; at most `PatienceLongest`, 240s). A pause that would end past the budget isn't taken, and the agent gets the error. While another member is busy too, the last one isn't first tried again alone (`passing`): the members take turns, and once the budget has begun, the same-one retries aren't taken either. While the budget lasts, the last candidate's failure is held (`newHoldWriter`), and a streaming agent is kept alive through the pause with SSE comments (`pauseAlive`). The try is traced with `Again` (the pause), `Replan` (how many are asked again) and `Patience` (the budget in seconds). The group editor's "Every member busy" row sets it. A plain provider keeps only the same-one retries `passing` gives the last one left. An agent that goes away in either pause (the same-one retry's or a group's replan) ends the request there with 499: nobody is asked again, and the try whose pause it was is marked `Gone` (#1894, heng91: a relay down while its proxy was off, the agent's window closed). The Routing page says the agent canceled the request before the retry and lists it as canceled, rather than ending its story on "tried again in 2s", a retry that never came (`TestAgentGoneInTheRetryPause`, `routing-agent-gone.test.cjs`). A try that answered is recorded (`served`, `answered`) for routing, affinity and usage. A try is added to the route's `Tries` only as it is asked, so a later try is the record that the gateway went on from this one, and the Routing page tells what came of a try from that, never from where it stood in the order (#2281, xishuchkui-code: an Antigravity 502 empty reply that went on to the next account was told as "an error another account wouldn't fix, so Claude Code gets it"). The one case the record can't show is the last try left out of its allowance after an earlier failure that wasn't one, where the agent is told the earlier error: that try is marked `Earlier` (`routing-went-on.test.cjs`).

## Constraints and failure behavior

- A fallback happens only while none of the reply has been sent. An agent never gets half a reply from one upstream and the rest from another.
- A refusal that comes as an error (#2400, Jichao). An error whose own `message` is, whole, `The request was rejected because it was considered high risk` is a refusal with no code beside it (`highRiskRefusal` in `policyRefusal`): in an HTTP error body or a stream's error event, never in an answer's text, which may quote it. The vendor that sends it isn't known; it says the request was turned away, so it goes to the next candidate under `RefusalRetries` like any refusal and rests nobody. A refusal error event before any content ends the try at once (`eventRefusalError`, `stop` as for any error), so an upstream that keeps the stream open doesn't hold the next candidate back; a refusal's stop or finish marker is still read to the end for the usage and terminator after it. After content, every write is read for a late refusal (`refusalAfter`), so one whose `event: error` name and data come in separate writes is still noted, and nothing is replayed. `TestHighRisk*`, `TestRefusalErrorDoesNotWaitForEOF` in [`refusal_error_test.go`](../../internal/gateway/refusal_error_test.go).
- A request is one usage record, counted once by how it ended (小一 on Discord: Codex on credits showed "5,482 · 1,094 failed" while rows said "2 tries/3 tries" and had been answered). The final record carries `tries` when the route took more than one (`rec.Tries`, from the trace's `Tries`). A try a vendor refused or turned away (`hw.refused`, `hw.turnedAway`) still writes its own record, for what it billed and why it failed, marked `handed_on`; `usage.Totals.count` skips such a record for calls and failures. A request failed only when the agent got an error (`LostRequest`); one answered after a failed try is counted beside it as answered on a retry (`Totals.Retried`, `RetriedRequest`, the `retried` filter). Logs written before `handed_on` are read the same way: the log index marks a failed, non-rejected record followed by another of the same route id as handed on (`routeRows` in [`log_index.go`](../../internal/usage/log_index.go)). Counts by account or route (`vias`, window holds) still count every try. A turn relayed on Codex's own ChatGPT sign-in is recorded as that codex account (`codexServed` in [`codex_backend.go`](../../internal/gateway/codex_backend.go)), so the account card's window counts it; the Routing view still names the seat OpenAI, an API-key call stays `openai` with no account, as does one whose `chatgpt-account-id` isn't the account Codex's auth.json here is signed in to (a Codex in WSL or under another `CODEX_HOME`), and a row already written without an account is left as it is. Those relay rows are still not a lead's answerer (`loggedAnswers`, #1367); a row an account answered, its host `host as email`, still is.
- Each record keeps the service tier three ways (#1784): `tier_asked` is what the client's body asked (`bodyTier`; Claude's speed fast reads `fast`), `tier_sent` is what that try's last request went out with, noted in `forwardOnce` after every rewrite (fast picks, Ultrafast to priority on a plan without it) onto the per-attempt `wireAt`, and `tier_served` is only what the reply said it ran at (`upstreamTier`, read by the sniffer and the translated readers), empty when it says nothing. The route's tries carry `tier` and `tier_served` the same way. A bridge that doesn't go through `forwardOnce` (the Claude subscription, Cursor's built-in) leaves `tier_sent` empty. Code: [`tier_record.go`](../../internal/gateway/tier_record.go).
- An agent's fast pick (`settings.FastPicks`, the bolt in its picker, #954) may also be in `settings.UltraPicks` (#1954), offered by the GUI only where one of Codex's accounts lists Ultrafast on the model (`provider.CanUltra`, `UltraModels`). `fastPick` marks its candidates `ultra`; a try of one goes with `service_tier: "ultrafast"` on Chat and Responses, and an agent on Messages carries it in the context (`withUltra`) to `forwardTranslated`, which sets `Request.Ultrafast` for the ChatGPT backend. Either way the same check as a client's own Ultrafast ask applies, now on Chat as well as Responses: an account whose list doesn't offer it is put after a mate that does (`tierMate`), or, with none left, sent `priority`. A Chat body's own `service_tier: "ultrafast"` is parsed as Ultrafast too (`chat.go`). `TestUltraPickSentUltrafast`.
- A usage record carries its prompt's cache beside `in` and `out` (#1839): `cache_read` (tokens read from the vendor's cache) and `cache_write` (cache creation, Anthropic's `cache_creation_input_tokens`; `cache_write_1h` the part written for an hour). `in` holds neither. Both are written on every record, 0 too, so a prompt that missed the cache reads as that. A record from before then has neither and reads as 0. Every route fills them: Anthropic's messages, Chat (OpenAI's `prompt_tokens_details.cached_tokens`, DeepSeek's `prompt_cache_hit_tokens`), Responses (`input_tokens_details.cached_tokens`) and Gemini (`cachedContentTokenCount`), passed through or translated, whole or streamed, a plugin's fetch, and the Claude subscription bridge. System One's decision calls report no cache. `TestUsageRecordsCacheTokensOnEveryRoute`, `TestPluginUsageRecordsCacheTokens`, `TestClaudeSubscriptionUsageKeepsCacheTokens`, `TestRecordAlwaysCarriesCacheTokens`.
- A request whose key is a Claude sign-in (`claudeSignIn`: `Authorization: Bearer sk-ant-oat…`, Claude Code signed in to claude.ai with agentlink as its base URL) is never told a 401, nor a 403 saying "OAuth token has been revoked". agentlink never passes that sign-in on, so such an answer is a provider refusing agentlink's credential, or one of agentlink's own Claude accounts lapsing; told it, Claude Code renews its own sign-in before each of its retries (ten for one request) and then asks to `/login`. Any error whose message mentions x-api-key, whatever its status, Claude Code tells as "Not logged in · Please run /login" too. It is told as a 502 in agentlink's words, an `api_error` saying "<provider> refused agentlink's credential (HTTP 401): …" with x-api-key said as "API key", and any other error such a request is told keeps its status with x-api-key said as "API key", as does a stream's error after its 200 (`keepsSignIn`, `claude_signin.go`). Recent calls and the usage log keep the provider's status and message. Any other 403, and a request with agentlink's key or an API key, is answered as before. The sign-in's beta (`oauth-…` in `anthropic-beta`) isn't passed on either (`askedBetas`), so a provider gets the request as Claude Code with agentlink's key sends it; a provider's own `header.anthropic-beta` still goes.
- A 2xx that can't be an API's answer is the 502 it stands for (`notAnAPIReply`, #1012): a web page (`text/html`, or a body that begins as one: a sign-in page, Cloudflare's challenge), a body with nothing in it, or one sent as JSON that doesn't begin as JSON. Every upstream request goes through it (`forwardOnce`, and the built-in clients' own: the ChatGPT backend's `/responses`), so it fails over, rests and is logged as a 502 does, its reason naming the page's title. Only the first bytes are peeked, which a stream waits for anyway, and a compressed body is left as it came.
- A 2xx from Zhipu or Z.ai holding the platform's refusal envelope (`{"code":1000,"msg":…,"success":false}`, which their Responses API at `/api/v1` answers a refused key) is the refusal it stands for (`provider.ZhipuEnveloped` in `forwardOnce`): 401 for a key refused, 429 for a limit or no balance, as Zhipu's error codes give, so it fails over and rests as those do and the agent is told why. `TestZhipuResponsesRefusalIsRefusal`.
- A streamed request is never left silent while its vendor says nothing. `holdWriter.watch` runs beside each try: past `keepHeldAfter` (15s) it sends a held try's agent the stream's 200 and SSE comments (`keepAlive`), none of the try, so another candidate may still answer in the same stream; once the reply passes, it puts a comment between two of its lines after `keepaliveEvery` of quiet. It stops after `keepaliveLongest` (5 minutes) with nothing from the vendor. A try waiting for its key's or account's slot or for room in its minute (`lanes.take`, `rpms.wait`) is kept alive the same way (`keepQueued`), for as long as it waits; once the 200 is out, the try is held, and its failure or its queue turning it away reaches the agent as the stream's error (`failTo`), not a status (coeo91 on Discord). A wait shorter than `keepHeldAfter` sends nothing, so its 429 keeps its `Retry-After`. A proxy in front such as Cloudflare (125s) otherwise ends the request (#947). Gemini streams get no comments (#934). ## Search results in translated Responses replies

When a search is done for a model (`searchReply`), or a Responses provider's
search is decoded for translation, its `KSearch` event and collected
`Search` part hold the query and pages found. [`responses.go`](../../internal/gateway/responses.go)'s
`responsesEncoder.event` and `renderResponses` return these as completed
`web_search_call` output items through the shared `responsesSearchItem`.
The action says `search`, carries both `query` (older clients) and `queries`,
and lists the nonempty source URLs in `action.sources`. An actual search
with no sources has an empty list; a text answer alone creates no search.

The stream adds and completes each search item, emits
`response.web_search_call.completed`, and keeps the same item in the final
response's `output`. Search events arrive after the search has run, so no
earlier progress is fabricated. Search items keep their order among text,
reasoning and client tool calls. They carry sources, not invented
`url_citation` annotations: the shared search result has no citation offsets
in the model's answer. Native Responses passthrough is unchanged. A client
that sends the item back in its next input (Codex replays its output) loses
nothing: `parseResponses` has no case for `web_search_call` and leaves it
out, as before.

This lets a Responses client verify search execution and display source
links without sending a separate Anthropic Messages request. Covered by
the `TestResponsesSearch` tests in
[`responses_search_test.go`](../../internal/gateway/responses_search_test.go)
and the Responses cases of `TestWebSearchForAModelThatCannot` in
[`search_test.go`](../../internal/gateway/search_test.go).

While a provider asked by `searchReply` is queued or thinking, sending only
keepalives or `response.in_progress`, `askTranslated` reads it with
`readSSEAlive` and hands on a `KAlive` event after `keepaliveGap` with
nothing else sent. It is nothing of the reply: `searchRounds` passes it on
uncollected, and `relay` takes it as the provider heard from, begins the
client's stream and sends the client's own keepalive (`enc.keepalive`).
Before, `relay` waited for the first content to make the client's encoder,
so Codex heard only the held stream's comments, which its idle timeout
doesn't count, and hung up after ~315s (#2316). An error before any
`KAlive` is still a status another account may answer. Covered by
`TestSearchQueueKeepsCodexAlive` in
[`search_queue_test.go`](../../internal/gateway/search_queue_test.go).

## A search API's base URL

Each search API ([`provider.SearchAPI`](../../internal/provider/search_api.go))
has an optional `url`, its base URL: an endpoint of the user's own that
answers as that API does (#1580). Empty is the vendor's own
(`SearchVendor.Base`); SearXNG has none, so its URL is required. `check`
takes only an `http://` or `https://` URL with a host and no `?query` or
`#fragment`, since `askSearchAPI` puts the vendor's path after it
(`/search`, `/res/v1/web/search`, `/v2/search`, `/v1/tools/search`) with the slash at its end
trimmed. The request goes through the gateway's client, so it follows
agentlink's proxy settings as the vendor's own address does
(`TestSearchFollowsTheSearchersProxy`).

The key is sent only to that URL. Go keeps Brave's `X-Subscription-Token`
and Exa's `x-api-key` across a redirect to another host, so `askSearchAPI`
doesn't follow one. The 3xx is the error, and it names where the search
was sent. agentlink ships and lists no third-party search endpoint; the URL
is only ever the user's.

A value the user set is never replaced by the vendor's default. In
Settings › Models › Web search the field sits under the key for every API,

already added fills in its saved URL, so Add with a new key alone keeps
the URL, and Add with no key changes only the URL. On the CLI,
`agentlink search add <api> <key>` keeps the URL set before, and `url=` with

## A search API's keys

A search API's `key` may hold several keys, separated by commas (#1477).
`askSearchAPIKeys` asks them in the order `searchKeyOrder` gives
([`search_keys.go`](../../internal/gateway/search_keys.go)), each with a
quarter of the search's time. By default they take turns (SlouchyQuill on
Discord, after dsh-tavily-pool): a counter per vendor moves the first key
asked on by one each search. `pick` `order` (`provider.SearchPickOrder`,
`agentlink search add … pick=order`, In order in Settings) always starts from
the first. Only a refusal (`searchRefused`: 401, 402, 403, 429, 432, 433)
goes on to the next key; any other error ends the search there.

A refused key rests (`searchRestFor`): 401 and 403 ten minutes ("turned
away"), 402 an hour ("out of credit"), a rate limit its `Retry-After` held
to 30 seconds through 10 minutes (a minute without one). 432 and 433 are
Tavily's plan and pay-as-you-go limits, out of credit from Tavily only; from
any other vendor they rest as a rate limit. A resting key is not dropped:
it is asked after every key that isn't, the one back soonest first, so a
search still has every key to fall back on. A key that answers wakes.
Rests are held by vendor and a hash of the key (`searchKeyID`), never the
key itself, and the vendor's error has the key masked
(`provider.MaskSearchKey`, `tvly-…abcd`) before it is logged or returned.

The query a search API, a Kimi Code plan's search service or WorkBuddy's
search is asked is masked as Settings → Privacy says (`maskedQuery` in
[`redact.go`](../../internal/gateway/redact.go); a plan set to go unmasked,
`provider.SkipsRedaction`, gets it as it is). A searcher model is asked
through `serve`, which masks its request the usual way. An agent's call to
the search MCP carries its query with the values put back, so before this
it went out as the agent wrote it (lc on Discord); `searchMCPRun` puts the
values back in what it returns (`redact.Restore`). What a model's own
web_search finds goes back to its vendor as found, placeholders and all.

What each Tavily key has used is read from `GET /usage` with that key
([`search_quota.go`](../../internal/gateway/search_quota.go),
`readTavilyUsage`): the key's own `limit` when it has one, else its account
plan's `plan_limit` and `plan_usage`, shared by the account's keys (a free
account's keys have `limit` null); both null is no limit. A read that fails
or a reply missing those fields is unknown, with why, never 0 used. A read
is kept two minutes (Tavily allows /usage 10 times in 10 minutes) unless
asked fresh. A key at its limit with no pay-as-you-go credit left rests an
hour as "used up"; a later read that finds credit wakes a key resting for
that or for being out of credit. Settings › Models › Web search shows a row
of the keys under an API with several or with Tavily's (In turn / In order,
each key masked with what it has used, Check again), and `agentlink search`
lists the same, read fresh.

Covered by `TestReadTavilyUsage`, `TestSearchKeysTakeTurnsRoundRobin`,
`TestSearchKeyRefusedRests`, `TestSearchRestFor`, `TestSearchQuotas`,
`TestSearchKeyNeverInFull`, `TestSearchAPIKeysTakeTurns` and
`search-keys.test.cjs`.

## Web search as an MCP server

`SearchMCPPath`, `/mcp/agentlink/web-search`, serves the same `webSearch` a
model that can't search is given (the searcher's model, a Kimi Code plan's
service, the search APIs, as Settings › Models › Web search orders them)
as an MCP server of its own, so Cursor, Claude Desktop or any agent can
mount it as a `web_search` tool (Kayphoon on Discord). It speaks Streamable
HTTP only: each POST of a JSON-RPC message or batch is answered with JSON
(`initialize`, `ping`, `tools/list`, `tools/call`), notifications get 202,
and GET and DELETE get 405, since the server has no stream or session of
its own. Legacy SSE isn't served; a client that only speaks stdio mounts it
through `mcp-remote`. The path has two segments under `/mcp/`, so it can't
hide a signed-in server's `/mcp/{name}`.

It is a gateway route like the others. `lanGuard` takes a gateway key from
another machine (only while agentlink is shared) and refuses a rebound browser
host, and the handler checks `local`/`sharedWith` again as a backstop when
`Handler` is served without `lanGuard`. Unlike other routes, a web page on
this computer (a `localhost` Origin, which `corsGuard` lets through) is
refused too: only an origin listed in Settings, which `corsGuard` already
held to a gateway key, may call it, as the MCP spec has a server check
`Origin`. `keyLimited` passes `/mcp/` by, so each `tools/call` reserves the
calling key's limit itself (`budget.Reserve`), and a spent key's call is a
tool error with no search made. The search is marked `CallFor{Agent, MCP:
true}`, so Routing says the agent called agentlink's web_search MCP tool rather
than that agentlink searched for one of its models. With nothing that can
search, the tool error says where to add a search API. Settings › Models ›
Web search shows the address (`#searchMcpRow`, from the Settings page's own
`gateway` address).

Its second tool, `web_fetch` (`search_fetch.go`, #2286), reads a page by
its URL for an agent with no fetch tool of its own. The URL is the agent's,
so it is downloaded as a caller's image is (`webFetchClient`, which is
`publicClient`): public addresses only, every resolved address checked and
pinned, through at most five redirects each checked the same, wherever
the request came from. It reads for at most 30 seconds and 5 MiB. An
HTML page is decoded from its charset and given as Markdown (`htmlText`:
headings, lists, links made absolute, code; scripts, styles and hidden
elements dropped), other text as it is, anything else is a tool error, and
so is a status of 400 or more. It answers `max_chars` characters (20000 by
default, at most 100000) from `offset`, and says the offset the rest starts
at. Each call reserves the calling key's limit as a search does.
`TestWebFetchReadsAPage` and `TestWebFetchOnlyPublic`.

A POST's body is read by `readMCPBody`, up to 1 MiB here and 32 MiB for
vision and for a signed-in server's `/mcp/{name}`. A longer body is refused
whole with 413, before any message in it runs or is passed on: the length is
told from the bytes read, one past the limit, not from Content-Length, so a
valid message padded past the limit is never run as its prefix (#1766).
`TestOwnMCPRejectsOversizedBody` and `TestMCPProxyRejectsOversizedBody`
cover it.

Covered by `TestSearchMCPServesWebSearch`, `TestSearchMCPWithNoSearcher`,
`TestSearchMCPGuarded`, `TestSearchMCPHeldToKeyLimit`,
`TestSearchMCPRoutedAsTheAgentsCall`, `TestSearchQueryMasked` and `search-mcp.test.cjs`.

## Image recognition as an MCP server

`VisionMCPPath`, `/mcp/agentlink/vision`, serves the model that describes
images to a model that can't see them (`seer`: Settings › Models › Image
recognition, else `AutoVision`'s) as an MCP server with one `analyze_image`
tool (JonahFu on X). `serveMCP` is shared with the web search server, so it
is answered, guarded and Origin-checked the same way, with a 32 MB body so
an image fits as a data URL, and each call reserves the calling key's limit
(`budget.Reserve`). The tool takes `image` and an optional `prompt`. With no
prompt it is described as a model's image is (`describe`, the same cache and
`visionSystem`); with one, `askVisionWith` asks the prompt beside it under
`visionAskSystem`. `image` is an http(s) URL or a `data:image/…;base64,` URL,
passed on as they are, or an absolute file path (`~/` and `file://` taken),
read into a data URL up to 20 MB when `http.DetectContentType` says it is an
image. A path is read only for a `local` caller: another machine's path
names nothing here, a shared agentlink's files aren't its callers', and a
request through a proxy or tunnel isn't `local`. The description's route is
marked `CallFor{Agent, MCP: true}`, so Routing says the agent called
analyze_image. Image recognition off or no model that sees is a tool error
that says where to pick one. Settings › Models shows the address
(`#visionMcpRow`, below Image generation).

Covered by `TestVisionMCPAnalyzesImage`, `TestVisionMCPWithNoSeer`,
`TestVisionMCPGuarded`, `TestVisionMCPHeldToKeyLimit` and
`vision-mcp.test.cjs`.

## Side models agentlink picks: allowance first

When agentlink picks the model itself (`AutoVision` for image recognition,
`autoSearcher` and the turn in `modelSearch` for web search), it picks
before routing runs, so routing has one provider to try and would try it
"all the same" while every account of it rests. Each request would then be
refused upstream again (#1801). `spentModel` (fallback.go) says a model is
out of its allowance when every candidate routing would try for it is
barred at a usage cap, resting for quota or credit (not for rate), or has
a full window (`candidate.full`), and when it is back. `smallModel`
(`smallReady`) prefers models that aren't spent, and the pickers rank a
provider with allowance above any tier or searchRank. With every one spent
they still name a pick, so `seer`/`Described` and `canSearch`, which tell
agents what agentlink offers, don't flip with a window. Such a pick isn't
asked: `askVisionWith` (`autoSpent`) answers with the reason and when it is
back, and `modelSearch` (`searcherSpent`) skips it, puts spent searchers
after the others and joins the reason into its error. A model named in
Settings is asked as before, and a searcher named there is not handed on
to another provider when it fails (see "A searcher that fails or finds
nothing"). Image and video generation (`AutoDrawer`,
`AutoVideomaker`) are not held this way.

Covered by `TestAutoVisionPassesOverOneOut`,
`TestAutoVisionTierAmongThoseWithAllowance`, `TestSpentModelAcrossAccounts`,
`TestVisionDoesNotAskSpentDescriber` and `TestSearcherPassesOverOneOut`.

## Disabled models

Settings › Models › Disabled models, `agentlink model disable|enable|disabled`
and `POST /api/settings/disabled-models` keep `settings.DisabledModels`
(#1867): patterns, each an exact id or a glob (`*` any run of characters,
`/` among them; `?` one), matched ignoring case against a model's
`<provider>/<model>`, its bare id and the bare id's last segment
([`internal/provider/disabled.go`](../../internal/provider/disabled.go)).
Nothing is disabled by default.

- Lists: `buildEntries` (`entriesOff`) leaves a disabled model out of the
  catalog, so `/v1/models`, the agents' model files and pickers, Codex's
  list, Muse and every routing group go without it; `membersIn`
  (`membersOff`) skips it as a member and `Deciders` as a decision model.
  `codexModels` drops a disabled one of Codex's own, and `codexListTag`
  changes with the list so Codex fetches it again.
- Requests: the gateway refuses it with a 403 in each API's shape
  ([`internal/gateway/disabled.go`](../../internal/gateway/disabled.go)),
  `model <id> is disabled in agentlink …`, at the choke points #882 holds keys
  at: `serve` (every chat, Responses, Messages and Gemini request, agentlink's
  own side calls, a session that was on it, a Codex sub-agent put on it),
  `perKeyBarred` (no candidate is planned for it: a group's next member, a
  provider's `Fallback`), `countTokens` and Gemini's `:countTokens`
  (`countOff`), `serveSystemOne`, `serveDecisionGroup` and `postDecide`
  (every decision call), draw, video and embeddings, and `codexBackend` for
  one of Codex's own bare models. A bare id the catalog no longer has is
  refused as disabled, not 404 (`provider.BareDisabled`). A group with a
  member left goes on without the rest; one with none left is refused,
  naming its disabled members (`provider.GroupDisabledOut`). A Codex
  sub-agent pick onto a disabled model is kept on its lead's model
  (`codexSubagentPick`, "it is disabled in agentlink").
- A settings.json that can't be read is never "none disabled": the list read
  last stays in force, and with none read since start every request is
  refused until it is fixed (`DisabledUnknown`); `SetDisabledModels` writes
  nothing over a file it couldn't read.
- Only requests through agentlink are covered: an agent signed in to the vendor
  itself is not, which the Settings row says.
- Tests: `TestDisabled*` in `internal/gateway`, `internal/provider`,
  `TestModelDisableCmd`, `TestDisabledModelsSetting`, and
  `internal/gui/tests/disabled-models.test.cjs`.

## Model ids without the provider

A client moved from another proxy (love1sbug on X, from CLIProxyAPI) keeps
asking for `gpt-5.6-sol`, and picks from `/v1/models`, where agentlink lists
only `codex/gpt-5.6-sol`. A bare request already routes (Model resolution,
above); the list didn't offer it. "Provider in model names" (`PlainNames`)
changes labels only, never ids.

Settings › Network and sharing › Model ids without the provider,
`POST /api/settings/bare-ids` (`settings.BareModelIDs`,
`provider.SetBareModelIDs`), off by default. On, `models` lists every row
it listed before, unchanged and first, then one row per bare model id
(`provider.BareEntries`, [`internal/provider/bare.go`](../../internal/provider/bare.go)):
the row of the entry that id reaches, with its label, under the bare id.
`GET /v1/models/{id}` answers a bare id the same way (`provider.BareEntry`).

- Which entry: the gateway's own resolution, so the list never offers what
  a request would not reach. A found or user group the id names (`groupForIn`,
  as `GroupFor`) gives the group's row; else `resolveIn` (as `Resolve`)
  gives the first provider in the Providers order that serves it. So a model
  several providers serve is listed once, and answered by its group with
  found groups on, else by the first provider, as before.
- An id already in the catalog as is (a group's or a provider's own id) is
  not listed twice. Group rows themselves add nothing.
- The target must be in the list shown: a gateway key held to some models
  sees only the bare ids that reach one of its models, so a key held to
  `b/*` doesn't see `glm-5.3` that would go to `a`.
- Never for another agentlink (`DrawersHeader`), whose remote provider would
  list each model twice, nor for Claude Desktop's list, which has its own
  shape.
- No agent file changes: agentlink still writes `provider/model` ids
  (`agentlinkModels`), so turning it on or off rewrites nothing.
- Tests: `TestBareModelIDsReporterCase` (Codex `gpt-5.6-sol` listed bare and
  answered on Chat, Responses and Messages, the list unchanged when off),
  `TestBareModelIDsShared` (several providers, found groups on and off, a
  held key, another agentlink) in
  [`bare_ids_test.go`](../../internal/gateway/bare_ids_test.go),
  `TestBareModelIDsSetting` in `internal/gui`, and
  `internal/gui/tests/bare-ids.test.cjs`.
- A URL agentlink downloads but didn't choose itself is downloaded from public addresses only, wherever the request came from ([`image_fetch_guard.go`](../../internal/gateway/image_fetch_guard.go)). That is an image a caller names (an `/v1/images/edits` or `/v1/images/generations` reference image, for an images API that takes files, Gemini's own API or Code Assist: `fetchPicture` in [`draw.go`](../../internal/gateway/draw.go), `publicClient`), a page `web_fetch` reads (`webFetchClient`), and an image or video a vendor answers by URL, which what the model was asked to draw or do can steer (the inline download for a `b64_json` caller in `draw.go` and `/v1/videos/{id}/content` in [`video.go`](../../internal/gateway/video.go), `vendorClient`; generate_image's own download in [`internal/imagemcp`](../../internal/imagemcp/imagemcp.go), `PublicClient`). Every address the host resolves to must be public (`publicAddr`: not loopback, RFC 1918, fc00::/7, link-local with 169.254.169.254, CGNAT 100.64/10, unspecified, multicast, documentation, reserved, Teredo, nor an IPv4-mapped, NAT64 or 6to4 form of one), and the request goes to the address checked, so a name that resolves elsewhere the second time changes nothing; a direct connection is checked again on the address dialled (`guardDialer`). Through a proxy the proxy is sent that address, never the name (an `https://` CONNECT or SOCKS keeps the name for TLS and Host; a plain `http://` URL through an HTTP proxy is asked for by the address in Host too). Each redirect, up to 5, is checked the same, and a caller's image must sniff as an image. A request from this computer gets nothing more: a reverse proxy or relay in front of agentlink on the same host makes every request it carries arrive from loopback, so where a request came from is never a reason to reach a private address. Two things are: settings.json's `fetchPrivate` (`settings.FetchPrivate`, none by default, no Settings page, this computer's own and never brought by a sync or restore), a list of names, `name:port`s, IPs and CIDR ranges the user lets agentlink download from (`allowFor`; a settings.json that can't be read lets nothing extra in), and for a vendor's URL the `host:port` of that provider's own endpoints, which the user named themselves (a provider on the LAN that serves its images from itself). A vendor's image that can't be downloaded is answered by its URL, never dropped; its video is a 502 naming why. A URL left for the vendor to fetch (a chat model's message) is the vendor's to fetch.
